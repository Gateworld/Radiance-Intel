# MTP draft head v2: the data the runner dumps (owner note 224 item 4)

2026-11-11, LoRA session (desk). This is for the runner (intel-host) and the coordinator. The trainer that reads this data is
ready and was tested on CPU: `~/code/lora-stack/mtp/train_mtp_v2.py`, README_v2.md.

**Why v1 failed (11-05):** the corpus was teaching/tools while traffic is broad, and the head was trained at depth 1 only.

## 1. Key decision: the 11-04 per-position record is enough for depth 1-3; extend the corpus, not the record
At depth d, row i of the unrolled head needs three things:

| what row (d, i) needs | where it comes from | already in the 11-04 record? |
|---|---|---|
| hidden input | `hidden(i)` at d = 1. At d ≥ 2 it is the head's OWN carry from row (d-1, i), which the trainer recomputes | yes |
| input token | t[i+d] (`meta.bin`) | yes |
| teacher for the token it drafts, t[i+d+1] | the trunk's distribution at position i+d (`top32.bin` record i+d) | yes |

- **Teacher forcing is the right case.** The engine scores round d only when round d-1's draft was kept, i.e. equals t[i+d].
- **The depth-d teacher is just the trunk's next-token distribution at i+d.** No "depth-d teacher" exists separately.
- **The head's own states must NOT come from the dump.** They change as the head trains; recomputing them is what fixes the depth-2/3 drift.
- **So the per-position format stays byte-for-byte the 11-04 format:** `meta.bin`, `hidden.bin` (4 hc streams, bf16, 20,480 B), `top32.bin` (256 B), ~20.7 KB a position.
- **The v2 requirements are about the documents:**
  1. **Every document complete and contiguous**, positions 0..L-1 in order. No prefix cut mid-document; MD3 lost documents 686-955 to the memory guard. The trainer asserts this.
  2. **L ≤ 2,045 positions.** At depth 3 a row's context is then ≤ 2,048, which the QSA indexer selects whole, so dense attention in training matches the engine.
  3. **Assistant turns are Flash-Next's own generations** (§3). Then t[i+d] is what the trunk actually emits.
  4. **Write in parts:** `flashnext-v2/part-01/`, `part-02/` … with ~150-200 documents each. Each part is a complete dump (meta, hidden, top32, role, corpus.jsonl, INFO). A guard stop then loses at most one part. The trainer reads `--dump .../flashnext-v2` and expands `part-*/`.

## 2. Three small new files (the v1 reader ignores them)
- **`role.bin`** (each part): uint8, one per position, in the same order as `meta.bin`.
  - Values: 0 = not generated by the model (system / user / tool result / template tokens, incl. the empty `<think></think>` the template inserts with thinking off); 1 = reply text; 2 = reasoning; 3 = tool-call text.
  - The model's own `<|im_end|>` counts as 1: the head drafts it.
  - The loss uses role ≠ 0 at the drafted token. This replaces v1's token heuristic.
- **`docs.jsonl`** (each part): one line per document.
  - Fields: `id`, `family`, `source`, `source_id`, `lang`, `thinking`, `turns`, `seed`, sampling params, `finish` (stop / length / tool_calls), `prompt_tokens`, `gen_tokens`.
  - If the engine's per-request `drafts= kept=` log fields are there (H121, 8b14a2d), also: `drafts` and `kept_by_position` [3]. These give the CURRENT head's acceptance on the same text, per family, so the offline proxy can be checked against the engine.
- **`parity2.bin`** (separate folder `flashnext-v2-parity/`, first 200 documents; extends the 11-04 parity file to 3 rounds):
  - Run as the 11-04 parity (`RADIANCE_MTP_PARITY=1`, `RADIANCE_MTP_DRAFT_HEAD_Q2=0`), plus depth 3, greedy drafts, coupling off (`RADIANCE_MTP_COUPLED=0`).
  - One record per document, at its last prompt row i: int32 request id, int32 i, int32 rounds (= 3), int32 x3 tokens fed at rounds 1-3 (t[i+1] = the trunk's greedy draw, then the round-1 and round-2 drafts), then for each round 1-3: 32 x int32 ids + 32 x f32 log-probs (the head's logits through the trunk lm_head, full-vocab log-softmax, largest first). That is 792 B a record.
  - Put the same run's meta / hidden / top32 for those documents beside it, as on 11-04.
  - **Why it is needed:** this is the only check that the trainer's rounds 2-3 match the engine. Round 1 passed on 11-05 (198/198). The rope position p+d-1, the carry = the pre-mixer `hw`, and the KV layout are taken from rad_block_mtp_hc.h but have not yet been tested. I check it on CPU before booking any card time.

## 3. Generation (intel-host, Intel engine; no production traffic, no user data)
1. **Serving setup:** the served container (`qwen3.8-next-flash-fp8-iq4r-moe.rad`, TP2) with **MTP on at the served depth 3** and the served draft head. Speculation never changes the text, so MTP on gives speed and the acceptance counters for free.
2. **Sampling: the model's defaults** (generation_config.json): temperature 1.0, top_p 0.95, top_k 20. Seed = document id.
   - Thinking ON for about 1/3 of documents (math, code, some chat). The reasoning tokens are drafted too.
3. **Length:** max_tokens = 2,045 - prompt tokens. Keep `length`-finished documents (prose capped at a length is a real family) and mark them.
4. **Multi-turn:** generate turn by turn. Every assistant turn is the model's own; user turns come from the source. Stop adding turns before 2,045.
5. **Tool calls:**
   - Render the source's schemas with the model's own chat template.
   - The tool result comes from the source's recorded function response (Glaive), or a fixed stub (BFCL).
   - Then generate the final answer.
6. **Dump:** the same KL-mode teacher-forced prefill as MD3 (`kld-gl.sh mtpdump`, `RADIANCE_DUMP_HWIDE=1`, `RADIANCE_MTP_DUMP=<part dir>`), over the rendered documents, part by part.
