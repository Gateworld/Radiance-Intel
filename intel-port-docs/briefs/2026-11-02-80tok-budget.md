# A step-time budget for 80 tok/s (owner notes 156 / 157)

2026-11-02, run 125. Measured numbers are from this milestone's runs (STATE.md). Estimates are marked E. Nothing here
is built yet: the note asks for this report first.

## 1. Where we are and what 80 tok/s needs

- **Today, MTP on, no flags (M215, rtneo:20):** 57.5 tok/s on the single warm prompt; the 11-request rotation median
  ~61, mean ~58 (H100-H105). The MTP head (depth 3) accepts ~0.70 a position, so a verify step yields **~2.93
  tokens**: one step is **~51 ms**.
- **80 tok/s at the same acceptance needs a 36.6 ms step: 14.4 ms less (-28 %).** If acceptance rose to 3.2 tokens a
  step, the target step would be 40 ms (11 ms less).
- **Where the 51 ms goes (P60's timeline, this run's instrument):** each card is busy ~84 % (~43 ms of kernels), idle
  inside command lists ~3 % (~1.3 ms of ~2 us gaps), and idle between lists ~13 % (**~6.0 ms**: ~3.7 ms waiting for the
  host to issue each draft pass, ~1.4 ms between steps, ~0.7 ms at one copy).
- **The biggest kernels a step (P65, format C on, device time):** trunk 4-row GEMV ~5.4 ms; hc group ~6.5 ms (+ norm,
  write, quant ~0.6); experts (format C) ~9 ms; all-reduce ~3.0 ms; GDN ~0.4; attention ~0.7; logits 0.68 (after
  a22ccb2); router top-k ~0.35 (profiled figures).

## 2. The budget, item by item

**Sum of items 1-8 (excluding 9-10): ~9-13 ms -> a 38-42 ms step -> ~70-77 tok/s on the single prompt.** 80 tok/s
needs the top of every range, or item 10, or higher acceptance (a better draft head, which would need training).
**My read: ~70 tok/s is reachable with items 1-4 (~7-10 ms); 80 is not likely without a structural change (item 2 at
full size plus a persistent-kernel style decode).**

## 3. Outside work surveyed, and what is not yet tried here

- **Megakernels / persistent decode** (Mirage MPK; Cohere's decode megakernel, 1.58x vLLM on one H100; Event Tensor;
  Fleet): fuse a whole forward pass into one persistent kernel, so no launch or host gap remains and operators can
  overlap. Not tried here. Our measured gaps (~7 ms a step) say this is where the large win is, but it is the biggest
  build on this list and there is no SYCL / Level Zero compiler for it.
- **Lookup-table GEMV for non-uniform codebooks** (FLUTE; T-MAC): restructure the weights offline and duplicate /
  vectorise the table to cut lookup cost; 2-4x over dequantise-then-GEMM at small batch (FLUTE's own claim). Partly
  tried: format C's LDS table; a wider 4-table form (IC2) was slower. FLUTE's offline restructuring is not tried.
- **All-reduce + RMSNorm fusion** (TokenWeave, MLSys 2026; NVIDIA's JAX/XLA one-shot all-reduce + norm): not tried;
  our hc_write fusion (note 142) is the same idea for a different neighbour.
- **Synchronization-free all-reduce** (SiFAR): for switch-based clusters; not applicable to two PCIe cards.
- **Speculative decoding**: EAGLE-3 / dynamic trees raise acceptance but need a trained draft head; a 2026 study finds
  tree drafting only slightly ahead of chains at batch 1, and MTP limited by one head reused across positions.
- **Level Zero mutable command lists** (the spec's extension): update kernel arguments in a recorded list instead of
  re-recording / re-issuing. This is the natural tool for item 2 (replaying the draft passes with new arguments).
  Not tried.
- **llama.cpp on the B70** (the same card): MTP 3.2x on short answers with Qwen3.8-27B Q8; env flags give +1-5 %
  (`SYCL_UR_USE_LEVEL_ZERO_V2=0`, oneDNN attention off). Nothing there beyond what we do, except that their GEMV path
  is reported at only 21-24 % of bandwidth -- ours is higher.
