## Facts that shape it

- RU_ANC_DUP = 1 and RU_ANC_FRD = 0 -> `fr == fb`: the replay ALWAYS reads the factor block the step then rewrites (and
  the dup copies at sf0 / sf2). So every factor write must follow every slice's replay READ of that block. That -- not
  the writes themselves -- is why v1 put all writes on the last arriver.
- The replay reads happen early (right after the anchor chain, ~the first 10 us); the writes happen after the token loop.
  In the common case every slice finished reading long before any slice reaches its writes.

## A. No serial tail: claim-based parallel factor writes (no spinning, no co-residency assumption)

1. Right after its replay reads (before the token loop), each workgroup's thread 0 increments a per-(sequence, key head)
   READERS counter (release fence first).
2. After its token loop, each slice reads READERS (acquire). If it equals VS, every replay read of fb is done: the slice
   CLAIMS its own share of the factor writes (an atomic flag / bit per share: (head, token, group) blocks split VS ways)
   and writes it, in parallel with the other slices. If READERS < VS it skips its share (leaves it unclaimed).
3. The workgroup whose increment made READERS == VS (the last reader), at the END of its loop, claims every share still
   unclaimed and writes those (usually none; at worst v1's full tail -- never worse than today).
4. The last arriver (the existing counter) keeps only the cheap parts: the marker stamp and the q|k conv-state rewrite
   (that one must wait for every slice's conv-history load). Counters / claim bits reset by the last arriver, as today.
Exact: every address gets the value v1 writes, written once, after every read of it.

## B. Batched per-token stores

Keep each lane's per-token factor-v (and its dup copies) and the onf row value in registers across the T <= 4 tokens;
store them after the loop (onf may go through SLM for a coalesced row store). Same values, same addresses. (V4: up to
-2.4 us at T 4.)

## C. Stage 2, minimal form: the per-token norms and gates once per workgroup, before the loop (no per-token barrier)

q / k for all T tokens are in SLM after the conv (cvq / cvk). Before the token loop, 8 lanes a (token, q|k) compute
sq / sk with EXACTLY one row-group's partition and order (16 per lane, then ru_row_sum<8>), and one lane a (head, token)
computes g, eg, bt -- written to SLM; ONE barrier; the loop then reads qs / ks / eg / bt instead of recomputing them on
every row-group. Removes 2 of the 4 per-token reductions, both rsqrt, softplus / exp / div from the loop. Exact if the
partition / order matches (check: hashes at T 1-4 + anchor-seq). NOTE: this also applies to the VS 2 split (one head's 64
rows a workgroup) -- bench it there too (S2), so the comparison stays fair.

## Order, gates, stop

Bench (5000 launches a process, one T a process, hashes = SPLIT 0 incl. anchor-seq x20, and a stress x500 for A):
1. A alone; 2. A + B; 3. A + B + C; plus the split + L1 + S2. The better form goes to the engine M-pair + prof.
Expected (bench, T 4, my estimate -- labelled as such): A ~27-28, A+B ~25-26, A+B+C ~19-22; the split + L1 + S2 ~17-19.
VS 8 wins only if C cuts its slope more than it cuts the split's (it shares one norm across 3 heads x 16 rows; the split
across 64 rows of one head). Stop rule: a hash difference that survives two fixes, or A+B+C not below the split + L1 + S2.
